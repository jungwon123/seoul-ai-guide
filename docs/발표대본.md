# Anyway (agt) — 발표 대본

> 총 7~9분 분량 · 슬라이드(`portfolio.html`) 흐름에 맞춤 · 구어체
> 굵은 글씨는 **강조해서 말할 포인트**, `(…)`는 호흡/제스처 메모. 수치는 코드로 검증된 것만 사용.

---

## 0. 오프닝 (약 30초)

안녕하세요. 서울 관광 AI 에이전트 서비스 **Anyway**를 만든 OOO입니다.
이 프로젝트는 "서울 어디 가지?"라는 자연어 한 마디를 입력하면, AI 에이전트가 장소·코스·이벤트를 **실시간으로 추천**하고 그걸 **지도 위에 바로 시각화**해주는 웹 서비스입니다.

(잠깐 멈춤) 오늘은 화면 데모보다는, 제가 프론트엔드에서 **어떤 기술적 문제를 만났고 어떻게 풀었는지** 다섯 가지를 중심으로 말씀드리겠습니다.

---

## 1. 프로젝트 개요 (약 45초)

기술 스택은 **React 19, TypeScript, Vite, Zustand**를 기반으로 했고, 지도는 **Google Maps**, 실시간 통신은 **SSE 스트리밍**을 사용했습니다.

구조를 한 줄로 요약하면 — (손으로 흐름 그리며) 사용자의 자연어가 **여러 에이전트로 라우팅**되고, 응답이 **블록 단위로 스트리밍**되어, 채팅과 지도 양쪽에 동시에 렌더링됩니다.

제가 집중한 건 이 흐름에서 생기는 **실시간성, 성능, 안정성** 세 가지 문제였습니다. 하나씩 보겠습니다.

---

## 2. ① 실시간 SSE 스트리밍 파이프라인 (약 90초)

(슬라이드 ① — 플로우차트 가리키며)

LLM 응답은 토큰 단위로 조금씩 도착하기 때문에 **실시간 스트리밍**이 필수였습니다. 처음엔 브라우저 표준인 **EventSource**를 썼는데, 여기서 문제가 터졌습니다.

EventSource는 연결이 끊기면 **자동으로 재연결**을 합니다. 그런데 채팅 요청은 멱등하지 않거든요. 즉, 재연결이 일어나면 **LLM 응답이 처음부터 다시 실행되는 루프**가 생겼습니다. (강조) 사용자 입장에선 답변이 갑자기 처음으로 되돌아가는 거죠.

그래서 EventSource를 버리고, **fetch와 AbortController로 SSE 파서를 직접 구현**했습니다. 자동 재연결을 없애서 루프를 차단하고, 프레임 버퍼링이랑 heartbeat 처리, 이벤트 타입 판별을 직접 제어했습니다.

(결과) 덕분에 **응답 준비 단계에서도 취소 버튼이 확실하게 동작**하게 됐고, 취소하면 질문 말풍선이 사라지면서 입력창에 텍스트가 복원됩니다. 표준 API를 그냥 쓰는 게 아니라, **왜 안 맞는지 이해하고 직접 만든** 경험이었습니다.

## 3. ② 16종 블록 → 통합 메시지 어댑터 (약 80초)

(슬라이드 ②)

두 번째는 데이터 구조 문제입니다. 백엔드는 한 번의 응답 안에서 **16가지 종류의 블록**을 스트리밍합니다. 텍스트, 장소 목록, 코스, 차트, 지도 경로… 형태가 다 다르고요.

게다가 **실시간으로 오는 데이터**랑 **DB에 저장됐다 다시 불러오는 데이터**가 필드 이름도 다르고, snake_case랑 camelCase가 섞여 있었습니다.

이걸 컴포넌트마다 분기 처리하면 코드가 금방 지저분해지죠. 그래서 **16종 블록을 단일 메시지 모델로 변환하는 어댑터 계층**을 한 곳에 만들었습니다. 정규화랑 필드 차이 흡수를 전부 여기로 모았고요. 렌더링은 **타입 기반 discriminated union**으로 블록별 컴포넌트에 분배했습니다.

(결과) 핵심 효과는 — (강조) **백엔드 스키마가 바뀌어도 어댑터 한 곳만 고치면 된다**는 겁니다. 변경이 격리되는 거죠. 그리고 OpenAPI 스키마에서 타입을 자동 생성해서 프론트-백엔드 계약도 동기화했습니다.

## 4. ③ 초기 번들 최적화 (약 80초)

(슬라이드 ③)

세 번째는 성능입니다. 이 앱은 Lottie 애니메이션, GSAP, Google Maps, 3D 엔진까지… 무거운 라이브러리가 많습니다. 그런데 **채팅만 쓰는 사용자가 3D 지도 엔진까지 처음부터 다 받을 이유는 없잖아요.**

그래서 세 가지를 적용했습니다.
하나, Vite의 **manualChunks로 vendor를 분리**해서 — Lottie 317KB, GSAP 71KB 같은 큰 덩어리를 메인 번들에서 떼어냈습니다.
둘, 지도·일정·북마크 패널이랑 라우트를 **React.lazy로 지연 로딩**해서, 첫 진입엔 채팅 화면만 뜨게 했고요.
셋, 여기가 포인트인데 — (강조) 사용자가 **장소나 코스를 추천받는 순간**, 아직 지도를 안 눌렀어도 **3D 지도 모듈을 백그라운드에서 미리 받아둡니다.** 그래서 막상 지도 탭을 누르면 대기 없이 바로 뜨죠.

"필요할 때만, 그리고 미리" — 이게 핵심 전략이었습니다.

(정직하게) 다만 LCP 같은 정량 지표는 Lighthouse로 전후 비교 측정을 더 해봐야 하는 단계입니다. 코드 레벨의 의도와 번들 분리 결과까지는 확인했습니다.

## 5. ④ 명령형 Google Maps 레이어 (약 70초)

(슬라이드 ④)

네 번째는 지도입니다. 추천 장소를 마커로 찍고, 카드를 누르면 해당 마커가 커지면서 강조됩니다. 그런데 순진하게 짜면, **선택이 바뀔 때마다 마커를 전부 다시 생성**하게 됩니다. 그러면 깜빡이고 비용도 크죠.

그래서 **마커를 만드는 로직과, 선택 상태를 입히는 로직을 effect 단위로 분리**했습니다. 선택만 바뀌면 마커를 재생성하지 않고 **스타일이랑 지도 중심 이동만** 갱신합니다.

(결과) 덕분에 깜빡임 없이 부드럽게 강조되고, 카드에서 마커로 넘어가는 FLIP 애니메이션도 GPU transform으로 처리하면서 **모션 민감 사용자를 위한 reduced-motion 가드**까지 넣었습니다.

## 6. ⑤ 협업 · 배포 내성 (약 70초)

(슬라이드 ⑤)

마지막은 협업과 배포 안정성입니다. 백엔드가 아직 배포 안 된 상태에서도 프론트를 개발해야 했는데요. **MSW로 19개 엔드포인트를 목킹**해서, 백엔드 없이도 전 기능을 검수할 수 있게 했습니다.

그리고 실제 운영에서 두 가지 사고를 막았습니다.
하나는, 예전에 개발 모드로 방문했을 때 남은 **Service Worker가 운영 환경 요청을 가로채는** 문제 — 진입 시점에 강제로 해제하게 했고요.
둘은, **새 버전 배포로 청크 해시가 바뀌면 캐시된 페이지가 옛날 청크를 요청해서 흰 화면**이 뜨는 문제 — 이걸 감지해서 **세션당 딱 한 번만 새로고침**하는 가드를 넣었습니다.

눈에 안 보이지만, **사용자가 사고를 안 겪게 만드는** 부분이라 신경 썼습니다.

## 7. 클로징 (약 30초)

정리하면 — (천천히) 표준 API가 안 맞을 땐 **직접 만들고**, 데이터가 복잡할 땐 **변환 계층으로 격리하고**, 무거운 건 **필요할 때 미리 받고**, 사용자가 사고를 안 겪게 **안정성까지** 챙겼습니다.

단순히 화면을 그리는 걸 넘어서, **왜 이렇게 동작하는지 이해하고 트레이드오프를 판단하는** 프론트엔드 개발을 하려고 했습니다. 감사합니다.

## 부록 — 예상 Q&A

**Q. 왜 EventSource 대신 fetch로 직접 구현했나요? 라이브러리도 많은데.**
A. 핵심은 **자동 재연결 제어**였습니다. EventSource는 재연결 동작을 끌 수가 없어서, 비멱등 요청에선 재실행 루프가 구조적으로 생깁니다. fetch+AbortController면 연결 수명을 제가 완전히 통제할 수 있어서, 취소·중단 시나리오까지 확정적으로 다룰 수 있었습니다.

**Q. 16종 블록 어댑터, 그냥 컴포넌트에서 처리하면 안 됐나요?**
A. 가능은 한데, 그러면 snake/camel 정규화나 라이브-저장본 차이 흡수가 **여러 컴포넌트에 흩어집니다.** 백엔드 스키마가 한 번 바뀌면 다 찾아 고쳐야 하죠. 어댑터 한 곳에 모으니 **변경 지점이 1개**가 됐습니다.

**Q. 성능 개선을 수치로 증명할 수 있나요?**
A. 번들 분리 결과(메인에서 Lottie·GSAP 격리, MapPanel 지연 로딩)는 빌드 산출물로 확인했습니다. 다만 LCP·INP 같은 **체감 지표는 Lighthouse 전후 비교 측정이 더 필요**하다고 솔직하게 말씀드립니다. 그게 다음 작업입니다.

**Q. 본인이 가장 어려웠던 부분은?**
A. ①번 SSE 재연결 루프였습니다. 처음엔 "왜 답변이 가끔 처음부터 다시 시작되지?"가 재현이 잘 안 돼서, 표준 API의 동작을 문서까지 파고들어 원인을 찾은 뒤에야 구조적으로 해결할 수 있었습니다.

- 수치는 검증된 것만(블록 16종, 엔드포인트 19개, 번들 크기). 모르는 지표는 "측정이 더 필요하다"고 정직하게.
